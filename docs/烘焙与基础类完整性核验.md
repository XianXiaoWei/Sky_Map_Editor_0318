# 烘焙与基础类完整性核验

**结论：Clump、Marker、Rail 都没有整个类完全复原。模型类与 Avatar 也没有完整验收。** 原函数子链对照通过，不能替代构造、原地图加载/启动、动态依赖、销毁和原游戏真机验收。自动清单中的阶段百分比不是游戏复原率。

## BstBaked.meshes 与 Objects 模型类

已有处理包括：读取 LVL0 v51/v52 的 LOD0，解析其中 Mesh.bin 记录，读取原 Mesh v28 模型的各 LOD/两个 half4 UV/法线/颜色/remap，展开每个渲染顶点 12 字节光照，并进入原 GLSL/原贴图 Vulkan 渲染。这里消费已有烘焙；**没有恢复重新生成光照的原 baker**。多层 LevelData IO/资源切换仍未闭合。

本轮新增原 LevelData 加载子链：

- 资源缺失后把加载记录 GUID 设为 `0xffffffff`，保留原保存 GUID。
- 采样数不匹配时，仍按序读光照和 opaque 块，释放临时分配，再清空整个 24 字节加载 LOD。
- 匹配时，opaque 块由 level heap 保留；原 Mesh remap 指定样本，uniform 使用样本 0。opaque 块不是 remap。
- 地图 `bakedResource` 改为加载后 GUID 线性首匹配，不再按名称＋GUID 过滤。模型消费者检查首个展开 LOD 的渲染顶点数，并使用被选记录自己的 remap 结果。
- CloudCard 使用同一加载表/原兼容检查，每个顶点将 12 字节烘焙中的前 8 字节复制到原 28 字节动态流；已有 356 个真实 CloudCard 全部满足此条件，接入云卡片 Vulkan 流。无烘焙的默认光照生成仍有明确预览服务边界。

原指令范围为 `0x1003f4c63..0x1003f4c6e` 和 `0x1003f4db5..0x1003f4f67`，单 LOD continuation 在 `0x1003f4d99` 返回。**这是原加载函数的子链核验，不是整个 LevelData::Load 的执行。** 资源存在性、serializer 和 heap 是显式准备服务；异步读取、ResourceRef 查询/Observe、加载/卸载、未检查的越界 LOD/remap、分配失败/异常展开还没验收。

原指令对照 11,563 组：252 组边界输入＋33 图 11,311 个真实烘焙 LOD，78,562,125 字节与服务调用顺序零差异。真实表共 10,653 记录：18 个缺资源记录失效；18 个 LOD 采样不匹配；共清空 36 个 LOD，11,275 个成功展开 LOD 的光照/opaque 字节与此前正确绑定结果一致。查询从保存关联变成加载关联后有 18 个对象失去无效记录，详见 JSON。

Rail 缓存对照限定非空点、已分配缓存和 `selfUpdating=false`。求值使用记录的 Linux sincosf/fmodf 服务；直接 JS sincos 曾有 12 组差异。弧长核验排除了 20 个不安全距离查询，不能将其算作通过。编辑器的轨道辅助线也不等于原游戏活动 Rail。

本轮没有把基础类的旧原函数证据改称新的整类原机验收；回归测试重放相关 fixture，缺口原样保留。后续模型/逻辑消费者应使用共享 loaded table、原资源引用/对象地址和明确服务接口，不能从保存字段或编辑器显示状态推断原游戏初始化/活动状态。
